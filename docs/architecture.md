# 構成と実装方針

## 技術の選択

| 技術       | 役割                       | 選んだ理由                                                 |
| ---------- | -------------------------- | ---------------------------------------------------------- |
| Vite       | 開発サーバーと配布用ビルド | ブラウザ向けの試作を小さな構成で始めるため                 |
| React      | 画面と入力フォーム         | サイトごとの画面・複数タブ・資料表示を部品に分けるため     |
| TypeScript | データとゲーム処理         | 予約状態や金額などの取り違えを開発中に見つけやすくするため |
| CSS        | レイアウトと装飾           | 架空のブラウザや予約サイトのUIを直接作るため               |
| Vitest     | ゲーム処理の自動テスト     | Viteの設定を共有でき、追加の設定が少ないため               |

初期版は1台のブラウザ内で人間とNPCを動かします。サーバー、ログイン、データベース、実際の航空券APIは導入しません。Unityは使用しません。

TypeScriptはESLint側の対応範囲に合わせて6.0系を使用します。新しいメジャー版への更新は、型チェックと周辺ツールの互換性を確認してから行います。

## ゲーム実装時の分け方

| 配置予定            | 担当するもの                                       |
| ------------------- | -------------------------------------------------- |
| `src/game/`         | 共通の型、在庫、予約、価格、ラウンド進行、集計     |
| `src/game/npc/`     | NPCの判断と、共通市場へ送る操作                    |
| `src/data/`         | 架空の人物・カード・旅行条件・便・シナリオ・調整値 |
| `src/ui/browser/`   | 架空PC、タブ、ゲーム内のページ切替                 |
| `src/ui/documents/` | 条件メモ、パスポート、カード切替                   |
| `src/ui/sites/`     | 比較サイト、3種類の予約サイト、入力手続き          |
| `src/ui/results/`   | 予約完了、ラウンド結果、総合結果                   |
| `src/app/`          | 画面とゲーム処理をつなぎ、試合全体を起動する部分   |

これらは配置予定です。まだ存在しない機能やフォルダーを実装済みとして扱いません。

## 状態の持ち方

画面の状態と、市場の判定を分けます。

- 画面：開いているタブ、選択中のページ、入力途中の情報、資料の表示面。
- 市場：共通の座席、価格帯の販売枠、サイトと手続きにひも付く確保枠、購入記録。
- 進行：ラウンド、開始時刻、締切、参加者の終了状態。
- 結果：購入額、実際の予約タイム、入力ミス・条件違反の内容、将来決める減点。

Reactの画面から市場処理へ操作を送り、処理結果を表示します。画面やタブがそれぞれ在庫を確定する構成にはしません。NPCも同じ市場処理を通します。

予約確定では「在庫があるか」「締切前か」「本人が未購入か」を一つの処理で判定して更新します。残り1席や同時の確定要求でも、二重購入を許さない設計にします。

## サイトごとの違い

- サイト1：確定まで確保しない。共通の空席と、最安料金の販売枠を確定時に確認。
- サイト2：手続き途中で確保。以降の画面は、その手続きの確保枠を参照。
- サイト3：閲覧人数に応じて変動し、予約確定時に価格を決定。

確保数の上限、確保の自動期限、自動解放の追加条件などは、設計の都合だけで追加しません。確定している解放条件は企画書に従います。

## 時刻と調整値

ゲーム処理に現在時刻を引数などで渡せるようにし、DOMや画面タイマーだけに判定を任せません。検索待ち、開始カウント、制限時間、NPC速度、価格幅は設定にまとめます。

調整値は[決定事項と検討事項](decisions.md)の区別を維持します。仮案を設定ファイルに移しただけで、正式なルールになったとは扱いません。

## オンライン化するとき

在庫・確保・価格・予約成否・締切の最終判定をサーバー側へ移します。ブラウザから確定価格や成功結果を自己申告させない構成にします。

今回の準備で通信方式やサービスを先に選びません。切断・復帰・通信遅延・表示価格と確定価格の差は、オンライン版の設計時に決めます。

## 確認の方針

CIはコード・型・テスト・書式・ビルドを確認します。テストはVitestで実行し、対象のファイルの隣に`*.test.ts`として置きます。ゲーム処理はDOMに依存させないため、ブラウザを模した環境を使わずにテストします。ゲーム処理を追加する作業の中で、テストも一緒に書きます。

優先するテストは、残り1席の競合、1人1件の購入、本人の未購入枠だけの解放、価格帯の販売枠、締切、同額時のタイム比較です。画面では80%・20%の配置、資料の可読性、タブ切替、入力の保持を確認します。
