# 最初に遊べる版までの実装順序

各段階を、さらに小さな作業（1つのPRで確認できる大きさ）へ分けて進めます。ここに書いたものは予定です。

## 0. 開発準備

- 起動確認ページ、TypeScript、コードと書式のチェック、テストの実行環境、ビルド。
- README、環境構築、構成、作業手順、未決定ルールの整理。
- Issue・PRのひな形、GitHub ActionsのCI設定。

完了条件：依存関係をインストールし、`npm run check`と`npm run build`が成功する。ローカルの起動確認ページを開ける。GitHub上でCIが成功する。

## 1. 画面の基本配置

最初の作業はここから始めます。

- 左80%の架空PC、右上の条件メモ、右下のパスポート。
- パスポートと架空カードの切替。
- 右側資料が読めることと、キーボード操作時のフォーカス表示。

完了条件：横長画面で指定の配置になり、資料を切り替えて内容を読める。まだ予約機能は必要ない。

## 2. 架空データと進行の土台

- 人物・カード・旅行条件・便・参加者・ラウンドの型。
- 1ラウンド分の架空データと、仮の調整値。
- 開始前の半透明グレー、資料の`?`表示、10秒カウント、開始後の情報公開。
- 共通の時間管理と、試合を初期状態へ戻す処理。

完了条件：開始前は資料の答えが見えず、開始時に全参加者へ同じ内容が渡る。再開始で前の状態が残らない。

## 3. 比較検索と複数タブ

- ゲーム内ブラウザのタブ追加・切替と、入力状態の保持。
- メモに合わせる検索フォーム、段階的な検索演出（検索時間は`src/game/settings.ts`の仮の値）。
- 便の候補、検索欄では絞り込めない条件の詳細、3サイトの価格表示。

完了条件：別タブで検索を進めても、元の入力と検索の進行が残る。実在のサイトは開かない。

## 4. 共通在庫と予約処理

ここは、在庫管理、確保、確定、解放を別の小さな作業に分けます。先にゲーム処理のテストを用意し、その後で画面につなぎます。

- 共通座席と、価格帯ごとの販売枠。
- サイト1の確定時チェック、サイト2の途中確保、サイト3の確定時の価格。
- パスポート・カードを参照する手続き。誤入力の扱いは企画書に従う。
- 何枠でも確保できること、1人1件だけの購入、購入時の他の未購入枠の解放。
- 予約成功時のグレー表示、チケット、右下の価格。

完了条件：残り1席を同時に購入しようとしても成功は1件。確保中の席を他サイトで重複購入できない。購入済みの席は解放されない。

## 5. NPCと市場の競争

- 人間と同じ市場処理を使うNPC。
- 検索・入力・確保・購入までの時間と、サイトの好み。
- 閲覧人数による価格変動。人数の数え方は仮案を明示。
- 人間1人＋NPC9人を基本にした試作と、在庫・価格の調整。

完了条件：NPCの行動によって枠が売れ、閲覧人数と価格が変化する。人間の操作に合わせて結果だけを後から作らない。

## 6. 結果と4ラウンド

減点のルールは案C（docs/decisions.md）に決めました。割合はプレイテストで調整します。

- 締切と、未予約者の最高値扱い。
- ラウンド終了時の誤入力・条件違反の判定と、決定した減点の表示。
- 今回の順位、現在の総合順位、同額時のタイム比較。
- ラウンドごとの資料変更、4ラウンド進行、最終結果。

完了条件：購入額・タイム・違反・減点を区別して説明でき、決定したルールで4ラウンドの結果を再現できる。

## 7. プレイテスト

- 検索待ちが別タブで判断する時間として機能するか。
- 右側20%の資料が読め、入力と見比べられるか。
- 3サイトをそれぞれ選ぶ理由があるか。
- 枠の抱え込みに、操作時間を使う戦略としての意味があるか。
- 売り切れ後に立て直せるか、4ラウンドで逆転の余地があるか。

初期版の調整が済んでから、オンライン対戦の通信・切断・サーバー判定を設計します。初期版の準備段階で、オンライン用のサービスやアカウントを増やす必要はありません。
